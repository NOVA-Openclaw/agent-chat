## Requirement 2 — Agent name from `pgConfig.user`, never `cfg.agents.list`/`default`/`"main"`

Source basis: `plugin/src/channel.ts:24-28` `resolveAgentName(cfg)` currently
reads `cfg.agents?.list`, finds `.default`, falls back to `"main"`. Step 2
finding confirms NEW build's `cfg.agents.list` is an internal projection with
`.default` markers removed (`config/types.agents.ts:61-67`,
`agent-list-projection.ts:5-16`, `legacy.roster.ts:199-217` on `d6c4379`),
so the lookup silently degrades to `"main"`. The fix takes the name from
`pgConfig.user` (already loaded via `loadPgEnv(undefined, "agent_chat")` at
module scope in `channel.ts`), which is guaranteed correct because
`send_agent_message()` already requires `sender = session_user`
(`schema.sql`, `enforce_agent_chat_function_use` validation in
`send_agent_message`).

## Gaps / open questions (flagging before implementation, not blocking test design)

1. ~~**TC-23-039 (Req 4, orphaned `received` re-check mechanism).**~~ **RESOLVED by I)ruid ruling (SE#1068 Step 4).** Startup performs no delete, no re-check, and no re-dispatch of any kind. A `received` row counts as processed; an orphaned `received` row is surfaced only via the startup digest (Requirement 5) as an unresolved item. See updated TC-23-039/040. No longer a gap.
2. ~~**TC-23-095 (Req 7, broadcast `'*'` recipients in the one-time cleanup).**~~ **RESOLVED by I)ruid ruling (SE#1068 Step 4).** Broadcasts are excluded entirely from the one-time >7d expiry cleanup — no roster enumeration, no rows written for them, regardless of age. See updated TC-23-095 and new TC-23-101. No longer a gap.
3. **TC-23-073/078/079 (Req 6, cross-agent `chat_ids` behavior).** Whether `mark_agent_chat_status` raises an exception vs. silently no-ops when the caller's array mixes owned and non-owned ids is not pinned down in the Step 2 text beyond "only on the caller's own rows." Both behaviors satisfy the literal security requirement; the test cases record whichever is actually implemented rather than presupposing one, but the implementer should pick one deliberately (silent partial-success is friendlier for the digest's "mark several at once" UX; an error is more defensive). Recommend silent partial-success given `mark_agent_chat_status` is meant to be called from a digest-driven bulk cleanup by the agent itself.
4. ~~**TC-23-084 (Req 6, third-party `reply_to`).**~~ **RESOLVED by I)ruid ruling (SE#1068 Step 4).** `p_reply_to` is now rejected outright for third parties (neither a recipient, nor the original sender, nor replying to a broadcast) — see the updated Requirement 6 source basis and TC-23-084/088/089. No longer a gap.
5. ~~**TC-23-005/007 (Req 1, `requestHeartbeatNow`).**~~ **RESOLVED by I)ruid ruling (SE#1068 Step 4).** `requestHeartbeatNow` feature-detection is dropped; it was never named in Requirement 1's source-basis deprecated-function list (`dispatchReplyFromConfig`, `createReplyDispatcherWithTyping`, `finalizeInboundContext`) and TC-23-005/007 never tested it — no case changes were needed. No longer a gap.
6. ~~**TC-23-058 (Req 5, cap=20 "0 remaining" note).**~~ **RESOLVED by I)ruid ruling (SE#1068 Step 4).** At exactly cap=20, the remaining-count line is omitted entirely (never "0 remaining") — see updated TC-23-057/058/059. No longer a gap.
7. **TC-23-016 (Req 2, config-loader seam, layer).** Whether the NEW build's real config-loading pipeline can be exercised as a standalone UNIT-level import (fast, no gateway process) or requires a running gateway (STAGING) depends on internal coupling in `d6c4379`'s `loadConfig`/agent-roster code that I have not fully traced function-by-function.
